# ros2-bridge

Мост между сервером и ROS2-стеком одного робота: подписка на топики, нормализация сообщений,
публикация команд с дедупликацией и ожидание обратной связи с таймаутом.

## Что решает

ROS2 отдаёт данные в «сыром» виде: `nav_msgs/Odometry`, `sensor_msgs/BatteryState`,
кватернионы, `builtin_interfaces/Time`, батарея в долях единицы. Серверу нужны SI-единицы и
проценты. Преобразование и валидация собраны в одном слое — `contracts.py`, — чтобы ошибка
«батарея 0.87 против 87 %» не расползалась по коду.

## Границы

```
ROS2 (rclpy) ──Transport──▶ RosBridge ──▶ RobotTelemetry / FeedbackRecord
                                  └──publish──▶ /robotX/task_command
```

`Transport` — единственная зависимость от ROS2. В продакшене — обёртка над `rclpy`,
в тестах — `FakeTransport` (записывает публикации, умеет инжектить сообщения).
Поэтому интеграционная логика тестируется без установленного ROS2.

## Поддерживаемые топики

| Топик | Тип | Что даёт |
|---|---|---|
| `/robot{robot}/odom` | `nav_msgs/Odometry` | позиция, курс (yaw), скорости |
| `/robot{robot}/battery_state` | `sensor_msgs/BatteryState` | заряд в % (`percentage × 100`) |
| `/robot{robot}/task_feedback` | внутренний контракт | статус задачи, прогресс, ошибка |
| `/robot{robot}/task_command` | исходящий | команда с `command_id` |

Неизвестные топики и чужие namespace'ы не роняют мост: они считаются в `stats.unknown_topics`.

## Правила, которые важны на практике

* Кватернион должен быть нормирован (`|norm-1| ≤ 0.01`) — иначе кадр считается битым.
* `percentage` строго `0..1`, как в спецификации; значение `87` отклоняется, а не «исправляется».
* Сообщение с меткой времени из будущего (> 30 c) или сильно старше текущего состояния
  отбрасывается: перезапуск робота не должен откатывать позицию назад.
* Повторная публикация команды с тем же `command_id` не уходит в ROS2 —
  это страховка от at-least-once доставки из брокера.
* `wait_feedback` взводит таймаут: потерянный `succeeded` не должен вешать диспетчер.
